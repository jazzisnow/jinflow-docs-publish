Collaboration Guide

jinflow uses git for collaboration. Every tenant AFS is a git repository from birth. Teams share work through GitHub (or any git remote).

Two protocols, one team

jinflow’s collaboration runs on two protocols, each suited to a different tempo.

  • Async authoring runs on git: two authors collaborate through branches, pull requests, and jinflow afs push/pull. Conflicts are structural and resolved with merge tools.
  • Live looking runs on P2P2P: the data owner starts a proxy, viewers click the link, everyone sees the same live data. When the meeting ends, Ctrl+C unplugs everything.

This guide covers the git-based mode.

Inviting People

Section titled “Inviting People”

Tenants are private by default

Any URL whose first path segment names a tenant requires authentication, regardless of which host serves the request. To publish a tenant for anonymous browsing, add it to the public_tenants allow-list in explorer/hosts.yml — that’s the only way data leaves the auth wall.

A new tenant ships locked; a typo in a host config can’t silently expose it. The audit surface is the short allow-list, not the much longer “everything you didn’t think to block.”

A principal is a person (or role, or group) recognised in a tenant. Each principal carries a stable slug (principal_id), a display name, and — for human users — an identity like owner, analyst, or viewer that determines what they can do.

Identity authority lives in Clerk

When you invite someone, the assignment is recorded on their Clerk account in publicMetadata.jinflow.tenants. The AFS holds a materialised view; the KLS bakes the display data. JinDesk reads from both at runtime — auth from Clerk (live), display from KLS (cached). See Sense 46 — The Roster for the full model.

Section titled “Send an invitation”

This:

  1. Writes afs/principals/user_alice.yaml locally
  2. Fires a Clerk invitation email to alice@example.com

Alice receives the email, clicks the magic link, signs up (or signs in if she already has a Clerk account), and lands on the tenant page.

Removing Someone

Section titled “Removing Someone”

This:

  1. Calls Clerk to surgically remove publicMetadata.jinflow.tenants["numetrix.rmc"] from Alice’s record — other tenant assignments she holds are preserved
  2. Marks her YAML status: archived and stamps left_at (the file stays — analytical authorship references continue to resolve)
  3. Refuses self-revocation (you can’t lock yourself out)

After jinflow ship, Alice’s access to the tenant disappears. She keeps her Clerk account; she just no longer belongs to this tenant.

Re-inviting

Section titled “Re-inviting”

If you revoke someone and later want them back, re-run jinflow invite with the same email and slug. The archived YAML gets resurrected with fresh active state; a new Clerk invitation is sent. Lifecycle history (previous clerk_user_id, accepted_at, left_at) survives in git.

Consent is a one-way door each direction

A human’s identity record can never be modified by another human without their consent. Not even by the owner of a tenant. The invitation email is the consent surface for enrollment; opt-out (user-initiated removal from a tenant) is the symmetric direction and is the subject of an in-app surface still being designed. See Sense 46 §10 for the full architectural principle.

Auto-Commits

Section titled “Auto-Commits”

jinflow make auto-commits a structured one-liner after each build:

jinflow afs update --do-it auto-commits after syncing pack content.

These auto-commits create a build logbook visible via jinflow afs log.

Conflict Resolution

Section titled “Conflict Resolution”

jinflow afs update uses three-way merge (SHA-256 manifest):

  • Only pack changed → safe update (auto-applied)
  • Only tenant changed → preserved (your customization wins)
  • Both changed → conflict (NOT overwritten, flagged for manual resolution)
  • Force mode → --force makes pack win on conflicts

jinflow afs pull uses fast-forward only. If local and remote diverge, it tells you to resolve manually with git pull --rebase.
