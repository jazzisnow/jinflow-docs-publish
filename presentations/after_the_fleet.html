After the fleet

Four topics, chosen by Mig: the fleet, the DAW, JinAPI, and use‑case documentation — especially administration.

They look unrelated. They are the same move made in four places, which is the argument this deck makes on the next slide — and the reason the order they get done in matters less than doing all four.

Standing. The fleet has its own deck and its own decisions; this one does not re-argue it. The other three are unruled — but not unwritten: the DAW and JinAPI each have a spec and an author already, and what is missing in both cases is a decision and a first line of code, not a design.

01The frame

Each one moves something out of your head and into the system

jinflow currently works because a particular person knows things: which tenants this machine serves, what may be asked of it over HTTP, what happens to a number after Gold, and what to type when somebody joins. None of that is written where the system can be asked. All four topics are the same conversion.

03Spec, not builtThe DAW

Gold is the sacred raw take. Everything after it is an insert.

sister‑7's spec, doc‑first, vocabulary settled with the sisters: a plugin is a processor type plus an I/O contract; an instance is that plugin placed, with a preset and an input binding; the dataset it emits is a stem; a render is the routing graph executed as N make‑calls; a scenario is a whole AFS state, implied by a git branch; a generation is a data delivery.

Two rules carry it: a KLS is a container (scenario, generation), not a coordinate, and only a scenario is a git branch — instances are peers, there is no base. The build is a DAW that bounces rather than plays live, which is exactly what keeps every render reproducible.

Why it is the biggest bet of the four. Everything jinflow computes today is SQL a person wrote. The DAW's first non‑SQL plugin — PMF on the aeros flagship is the candidate — is the moment the engine stops being dbt with a very good surface and becomes a processor host. That is a product ceiling question, and it is the only one of the four that does not get more urgent by waiting.

And the build side is already written: make --from <kls>. The seam is at gold — make cuts the take, everything after gold is a render — so the flag names an existing KLS to build on rather than re-cutting from source. --from gold is the ergonomic default (this tenant's working KLS); --from <snapshot> forks a new KLS off a frozen take; --from <base> --scenario scn_x forks a cheap what‑if. (the_build_graph.md, s7 with Mig.)

That flag is the cloud requirement, and it is why this is not only an analyst's feature. A KLS in the cloud has no source/ beside it — the take cannot be re-cut there. Rendering from the gold already inside the container is the one build operation that is possible, which makes --from the mechanism by which a cloud KLS can be extended at all. sister‑9's Processor doc names the same primitive in your words: a processor extends the surface of a given KLS by an additional contract.

Status   Spec only. --from exists in the CLI today on ops restore and ops rewrap, nowhere near make.

Open   Does a forked scenario copy the base's gold into its own file or reference stems by content‑address from a shared store — a KLS is one DuckDB file, so this is a real decision and the deeper of the two. Then: does a plugin run in‑process or out, and what does a stem cost in a store we ship whole.

04Word is new, thing is notJinAPI

How a JinServer becomes connectable — and the first caller is an agent

grep -ri jinapi over the repository returns nothing. But the thing has a spec, an author and a ruling already, so the only genuinely new part is the word — and that is a naming decision, not a design one.

PieceIsStanding
The Wirethe outward contract — Read, Write, and a Catalog facet for discovery. “There is no jinflow ↔ jinflow surface. There is only a jinflow ↔ everything surface.” Sense 30, proposed
JinServerthe host: JinDesk with the browser taken off, one tenant, many per machine — serves nothing but the Wire specced, not built
MCPone transport of the Wire, not a parallel protocol. tools/list ← Catalog + write verbs; resources/list ← Catalog + Read ruled 2026‑08‑27 (Mig × s9)
Identitya Pass, like any other consumer — an agent gets no special doorthe existing model

Why MCP changes who arrives first. A human integrator needs a customer, a contract and a reason. An agent needs a URL and a Pass. So the Wire's first outside consumer is likely to be a model rather than a company — which is cheap and early, and also means the first thing that ever calls this is something that will try every verb it is shown. jinflow already speaks the tool shape internally, via Vera (evolve/tools.ts); the MCP binding externalises exactly those tools to a caller that is not trusted in‑process.

So what does the word do? We have just spent a whole deck removing three qualifiers that named one noun. JinAPI has to name something Wire, JinServer and MCP do not — and it does: the faces are what runs, the Wire is what is spoken, and JinAPI is the Wire made reachable by someone who is not us. That is a third slot the naming doc does not have: not how a person meets it, not how a system meets it, but what is spoken — a contract, not a face.

Open   Which rung: a word we use in prose (free), a supported surface (versioned, documented, deprecation policy), or a product (keys, quotas, someone answering when it breaks). The trap is climbing that ladder without deciding — a name a caller has integrated against is a foreign key you can never rename.

05Missing readerAdministration

Three people use this system. One of them has documentation.

ReaderAsksHas
The analystwhat does this number mean, and where did it come from 12 guides in docs/guide/, in three languages
The administratorsomebody joined. Somebody left. This tenant must go public — no, dark. Who can see what? a verb list. invite · appoint · appointments · revoke · sync-principals · ops policy are all in the CLI reference, and nowhere in a document that describes a situation
The operatorit is deployed. Is it healthy? What did it just do? 25 files in docs/operations/ — runbooks, a diagnosis from May, a to‑do list, and two called Untitled-1.md and Untitled-2.md

A list of verbs is not documentation — it is an index to documentation that was never written. The administrator's document is situation‑shaped, not command‑shaped: you have been handed an installation · somebody joined · somebody left, today, angrily · this tenant must become public · this tenant must go dark · the numbers were wrong and are now right.

And it is the only one of the four that can be written today: every verb it would document already exists and already works. What it needs is a decision about who it is for — you, a customer's IT department, or us — because that choice sets its whole voice.

06Sequence

A working order, which is not the order they were listed in

  1. Fleet — no longer holding a branch, and now worth finishing.The blocking ruling landed on 8 September and the resolver shipped with it. What is left is consolidation rather than decision: three unhurried rulings, and folding what was settled out of this deck and into the papers that outlive it — which is the step that actually ends a topic.
  2. JinAPI — because the design is done and only the promise is unnamed.The Wire is specced, MCP is ruled as its transport, the JinServer is designed to serve nothing else. What is unsettled is which rung the word claims — a term of prose, a supported surface, or a product — and that is a conversation, not a project. It also completes the names doc, which currently has slots for what runs and none for what is spoken.
  3. Administration documentation — because it can start before anything settles.The verbs exist. The situations exist. The only prerequisite is naming the reader. It is also the cheapest possible rehearsal for a first outside user: writing down what somebody else would have to do is how you find out they cannot.
  4. The DAW — and its first slice may be a flag, not a plugin.The bet is the first non‑SQL processor, and that needs a date rather than a queue position. But make --from <kls> is specced, small, and load‑bearing for the cloud: without it a cloud KLS cannot be extended at all, because there is no source/ up there to re-cut from. Building the flag first buys the cloud capability and lands the DAW's build side, before anyone writes a processor.

What this deck asks for   Three sentences, one each: which rung JinAPI claims (a word · a supported surface · a product) · who the administration document is for · whether make --from is built before the first processor. The fleet's rulings live in their own deck and are not re-asked here.
