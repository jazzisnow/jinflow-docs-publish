The Atelier — Authoring the Analytical Framework

Dieser Inhalt ist noch nicht in deiner Sprache verfügbar.

The workshop where the AFS gets written. One surface, many artifact tiers; one writer pattern, many file types; one branch context, many ways to forget it’s there.

The Atelier (Sense 29) is jinflow’s authoring environment for the B-tier of the architecture — the analytical framework itself. Where the Bell (Sense 33) is the substrate for things the system noticed about a tenant, the Atelier is where humans declare what the system should look for in the first place. Subject Matter, Signals, Theses, and (next) Verdicts: the YAML files on disk that jin make consumes to build the KLS.

The design constraint that makes the rest fall into place: the YAML files on disk are the source of truth, and every save is a git commit.

A-tier vs B-tier — the dividing line

Section titled “A-tier vs B-tier — the dividing line”

Two questions decide where an artifact lives in the tenant AFS git repo:

  1. Is it analytical content? Smebits, signals, theses describe how the tenant’s data should be interpreted. They differ between scenarios on purpose — “what if this threshold were 10 instead of 50?” is the entire point of branching.
  2. Or is it operational state? Notes, bookmarks, recents, bell resolutions describe how a particular human engaged with the tenant on a particular machine. They should not differ between scenarios — dismissing a ring once should dismiss it everywhere.

The first kind is B-tier. It lives on main and on every scenario/* branch, independently. Each branch can edit its own copy without affecting the others.

The second kind is A-tier. It lives on a dedicated orphan branch that shares no history with main. Every scenario reads the same orphan-branch content; the A-tier writer is branch-blind by design.

The Atelier writes B-tier files. The Bell, Notebook, Bookmarks, and Recents writers write A-tier files. The two paradigms coexist; the Atelier never touches the orphan branches, the orphan-branch writers never touch main or scenario/*.

What the Atelier writes

Section titled “What the Atelier writes”

Each artifact type is a folder of YAML files in the AFS root, with a loader on the read side and a writer on the save side.

TierFolderLoaderWriterSibling file?
1 (strategic prose)smebits/listSmebits() / loadSmebit()saveSmebit()—
2 (declarative shape)signals/listSignals() / loadSignal()saveSignal().sql (optional)
3 (narrative tier)theses/listTheses() / loadThesis()saveThesis()—
4 (root cause, planned)verdicts/(not yet shipped)(not yet shipped)—

All loaders live in src/lib/server/atelier.ts. All writers live in src/lib/server/atelier_writer.ts. The page-level Svelte editors at /[tenant]/atelier/{smebit,signals,theses}/[id] bind a form to the parsed YAML, validate live via an ajv schema mirror of the engine’s <artifact>check.py, and POST the cleaned JSON to a SvelteKit form action that calls the writer.

The writer pattern

Section titled “The writer pattern”

saveSmebit is the canonical shape; the other writers follow it.

Three properties worth naming:

  • Atomic write. fs.rename is atomic on POSIX. A half-written file can never appear on disk even if the process is killed mid-write.
  • Idempotent save. If git add produces no staged change, the writer returns the existing HEAD with an error: 'no_changes' flag. The Save banner says “Saved — no changes to commit.” No empty commits.
  • Semantic prefix. Every commit message is feat: <create|edit> <artifact> <id> via Atelier. The repo’s commit-msg hook enforces semantic prefixes; the writer cooperates.

For two-file writes (signal YAML + sibling .sql), saveSignal runs git add twice and commits both files atomically. The commit shows both files; the working tree is never partially-updated.

Where the branch comes in (and where it currently doesn’t)

Section titled “Where the branch comes in (and where it currently doesn’t)”

The writer calls git add + git commit in the AFS root on whatever branch HEAD points at. That’s correct B-tier behaviour: an edit made while checked out on scenario/lower-thresholds lands on that scenario branch only, and the corresponding edit on main lands on main only. Two parallel timelines for the same smebit, one per branch.

What the writer doesn’t do today: surface the branch context to the user. The Atelier editor’s chrome doesn’t say “this save will affect scenario/X only.” The user has to look at the BranchIndicator in the global navbar to know what branch they’re on.

This is a UX gap, not a correctness gap. The mental model needed to make it work:

  • If you want this edit in every scenario → check out main, save, then propagate to each scenario branch that needs it via git cherry-pick (today) or a future jin scenario rebase-style command (not yet shipped).
  • If you want this edit in one scenario only → check out that scenario branch first, then save.

Future improvement (sketched in letter-from-atelier-sister and refined in letter-to-atelier-sister-2):

  • Layout-level: expose currentAfsBranch in the page’s load data so every Atelier surface can read it.
  • Editor-level: a small “divergence badge” next to the artifact id that reports whether the file on disk matches main. Three states: identical (no badge), modified for scenario/X, new in scenario/X. Computed once per page load via git show main:<relpath> comparison.
  • Tenant-level (a follow-up route, out of editor scope): a scenario drift dashboard at /{tenant}/scenarios/{branch}/drift that reports artifacts the scenario has changed vs main + artifacts main has changed since the scenario was cut.

Capability gating

Section titled “Capability gating”

Two capabilities frame the Atelier surface:

CapabilityWhat it grants
afs:writeSaving any artifact in the Atelier. Same gate the Signal Builder writer uses (Phase B convergence).
afs:gitLower-level git operations on the AFS (currently unused at the route level; reserved for future advanced surfaces).

The gate is enforced in two places:

  1. Page-level: every Atelier route checks checkAtelierAvailability(tenant) first. If no AFS is reachable (cloud demo deployments with no JINFLOW_AFS_ROOT or JINFLOW_LIVE), the layout renders an explainer instead of the form. The cloud Atelier is read-only by construction.
  2. Action-level: every ?/save action calls requireCapability(event, 'afs:write'). A user with view:smebits but not afs:write can browse the editor in read-mode but the save action returns 403.

Demo mode (JINFLOW_DEMO=true, cloud) strips afs:write from the capability set. The cloud surface never writes.

The reader path

Section titled “The reader path”

Atelier reads from disk via fs.readdirSync + fs.readFileSync, not from the KLS. Three consequences:

  1. No jin make needed to see edits. The Atelier shows the current working tree of the AFS — committed or uncommitted. A save commits, so the working tree stays clean, and “from disk” is effectively “from the current git state.”
  2. Parse errors are surfaced, not swallowed. A malformed YAML still appears in the list with a parse_error chip; the operator can find it through the Atelier rather than chasing it in the terminal.
  3. Cross-link consistency. As of Phase B.5, Signal Builder also reads signals from disk via listSignals() / loadSignal() (with a KLS fallback for cloud). The two surfaces now show the same source of truth without needing a build between them.

The form architecture

Section titled “The form architecture”

Every Atelier editor binds a Svelte 5 $state form to a deep copy of the loaded YAML, runs ajv validation reactively, and renders:

  • Identity grid: id (readonly), type/kind/category enums, version, status. Whatever non-prose fields identify the artifact.
  • Tri- or quad-lingual blocks: subject / why / content / statement / interpretation. Locale tabs at the top of each block (EN / DE / FR / IT, driven by the tenant’s display.locales config), one textarea per active tab. Empty or TODO-placeholder cells get an amber dot on their tab so they can’t be silently left behind.
  • Optional blocks: smebit’s check (executable SQL), smebit’s prescription (remediation), signal’s sibling .sql, thesis’s evidence chain, thesis’s verdict thresholds.
  • Validation summary: at the bottom, friendly-pathed list of every JSON Schema error (humanizePath() from labels.ts maps /scope/tenant_id → “Scope → Tenant”).
  • Header: Cancel button (returns to the list, discards edits; data-sveltekit-reload forces a full navigation), Save button (gated on validation), small-text breadcrumb back-link (← Subject Matter, ← Signals, etc.).

The Save button is disabled until the form validates. The validation chip (valid / N error(s)) sits next to a green/red dot. After save, an inline banner shows the new commit SHA or “no changes.”

Multi-surface convergence with Signal Builder

Section titled “Multi-surface convergence with Signal Builder”

The Atelier and Signal Builder are two doors onto the same set of signal YAML files. Phase A cross-linked them with “Open in Signal Builder ↗” / “Open in Atelier ↗” buttons; Phase B routed Signal Builder’s save through saveSignal() so commits are uniform; Phase B.5 routed Signal Builder’s reads through the same disk loaders.

Phase C (planned, not yet shipped) embeds Signal Builder’s type-specific config panels (BalanceConfig, EntityFilterConfig, DuplicateConfig, EnrichmentConfig, MandatoryItemConfig) as panels inside the Atelier signal editor — so editing a type: balance signal in Atelier shows the a/b aggregate forms above the raw YAML/SQL panes, rather than leaving the author to remember the YAML schema by hand.

After Phase C, Signal Builder remains the wizard for new signals (cold-start, 6 steps, walks you through). The Atelier becomes the type-aware editor for existing signals.

Operational notes

Section titled “Operational notes”
  • The Atelier never reads or writes to the KLS or the SIS. Those are derived stores. The AFS YAML files are the source.
  • Save operations call git add + git commit synchronously via execFileSync. No worktree pool, no daemon. The cost is one git process per save; the benefit is that the writer can be reasoned about as a plain function of (tenant, id, parsed object).
  • The commit author is resolved via getGitIdentity(tenant), which reads git config user.name / user.email from the AFS repo. This is the same identity model the rest of the engine uses.
  • Filename = id. The slug guard (^[a-z0-9_]+$) is enforced on every read and every write. A crafted URL can’t escape the artifact directory.

When the architecture changes

Section titled “When the architecture changes”

If a future artifact tier should be A-tier (scenario-shared, operationally fluid), it joins ARTIFACT_BRANCHES in jinflow/cli/commands/afs.py and gets its own orphan-branch writer on the engine side. The Atelier wouldn’t touch it.

If a future artifact tier should be B-tier (scenario-scoped, analytical), it joins the Atelier’s pattern: a folder under the AFS root, a loader pair in atelier.ts, a writer in atelier_writer.ts, a route under /[tenant]/atelier/<tier>/, a schema + validator in src/lib/atelier/, friendly path labels in labels.ts.

The dividing line — A-tier vs B-tier — is what makes the rest of the architecture coherent. Pick the wrong tier and the artifact will fight the surrounding system: a B-tier artifact on an orphan branch can’t participate in scenarios; an A-tier artifact on main gets duplicated across every scenario branch by accident.

So: when in doubt, ask which question the artifact answers — how should the data be interpreted (B-tier) or how did this human engage with the tenant (A-tier).
