The glossary defines each word. This page shows how the words relate. Each view is one of the product’s models, plus a view of every word at once. Select a word to read its entry: its definition, what it is not, and every relation with the sentence that explains it. A link to this page keeps the view and the word, so you can share it.

These are the engine’s words, the ones every tenant shares. A domain pack adds its own words on top, and each tenant’s ontology in JinDesk shows them.

AFS Engine word

Artefact Store. The per-tenant git repository holding every declarative artefact: signals, theses, verdicts, Subject Matter, Dossiers, lenses, pipeline.yml, entities, contracts. The source of truth for what should be computed.

More

Artefact Store. The per-tenant git repository holding every declarative artefact: signals, theses, verdicts, Subject Matter, Dossiers, lenses, pipeline.yml, entities, contracts. The source of truth for what should be computed.

Also called: afs, artefact store, framework store

Relations

  • part of Tenant: Exactly one AFS per tenant, a git repository. Scenarios are branches inside it, not more AFSes.
  • is not OPS: Both hold human work. The AFS holds what was authored and committed; the OPS what was done while operating. Nothing moves from the OPS into the AFS by itself.
  • holds Subject Matter: Authored as YAML and committed.
  • has part Scenario: A scenario is a state of the AFS, held as a git branch, the only branch axis. There is always at least one: the default branch is the privileged scenario, not a base.
  • read by Make: One AFS commit per build. What it read is packed into the KLS as its Imprint; the commit is only the Imprint's id, and a dirty-tree build matches no commit.
  • holds Extractor: Declared in afs/scripts/pipeline.yml, the extraction contract. An extractor copies bytes; only a declared pre_sync hook may reshape.
  • is not Imprint: The AFS is what the next build reads, and it moves. The Imprint is what this KLS was built from, and it never moves.
  • written by JinDesk: Through the Atelier, which commits authored YAML to the tenant's AFS. The next make reads it.
  • holds Residency: Declared in the committed tenant.yml. A scenario may narrow it, never widen it.
  • read by console (jin console): To know what has been authored.
  • written by console (jin console): As a diff a human commits. The loop closes by authoring.

  • Atelier — authoring that commits into the AFS
  • About — AFS remote, archive size, Imprint delta

Aspect Engine word

The kind of grouping a fleet is: logical (lfleet), physical (pfleet) or organisational (ofleet). What makes an aspect that aspect is how many groups a tenant may belong to — one leaf of a tree, one place per presence, or many overlapping sets.

Is
the cardinality of membership that tells lfleet, pfleet and ofleet apart
Is not
the shape of the grouping — pfleet and ofleet are both trees and behave completely differently
More

The aspect is always spoken, never inferred (ruled 2026-11-17): a broadcast is broadcast --lfleet valais or --pfleet eu-west, and a bare broadcast valais is refused. The three aspects carry three blast radii — a message to an audience, an operation on everything running somewhere, a message to an organisation — and the dangerous one must never look like the safe one.

Also called: fleet aspect, lfleet, pfleet, ofleet

Relations

  • part of Fleet: Every fleet is read through exactly one aspect, and the aspect is always spoken at a broadcast (Mig, 2026-11-17).

DLZ Engine word

Data Landing Zone. An optional store outside the tenant that feeds its source/: when pipeline.yml declares one, Phase 0b copies changed CSVs from it into source/. A build reads source/, never the DLZ.

More

The DLZ is a separate repository laid out {dlz_root}/{pack}/{tenant}/{source_system}/csv/, which also holds the tenant's tenant.yml and logo. It is not the trust boundary: that is the extraction contract (pipeline.yml), which pins and verifies whatever crosses into source/. Per Sense 31 The Inlet.

Also called: dlz, data landing zone, source intake

Relations

  • feeds source/ (Delivered data): Optional. When pipeline.yml declares a DLZ, Phase 0b copies changed deliveries into source/.

Dossier Engine word

A human-curated narrative grouping of related Subject Matter — the story layer on top of atomic expert knowledge.

Is
a narrative wrapper that connects related Subject Matter
Is not
a perspective or automated grouping. Dossiers are hand-curated by a named curator
More

A Dossier is a human-curated narrative grouping of related Subject Matter. Where a single Subject Matter entry is atomic knowledge, a Dossier is a story — it connects multiple insights into a coherent whole (e.g., "Implant tracking from OR to invoice"). Maintained by a named curator. Not executable — the narrative organizes, it does not evaluate. The display label is configurable per tenant; "Dossier" is the default engine vocabulary.

Also called: dossier, bitbundle, bundle, use case

Relations

  • groups Subject Matter: By hand: a named curator tells a story across Subject Matter. No computation.
  • is not Perspective: Both group things. A Dossier is curated by a person; a Perspective is computed by rules.

Evidence Engine word

A weighted reference to a signal or Subject Matter entry that contributes to a thesis evaluation. Each evidence link has a role (primary, supporting, context, counter).

Is
a scored link between a thesis and its supporting/contradicting data
Is not
the raw data itself. Evidence is the *connection*, not the finding
More

In the thesis system: a weighted reference to a signal or Subject Matter entry that contributes to a thesis evaluation. Each evidence link has a role (primary, supporting, context, counter) and a numeric weight. In findings: machine-readable data attached to each finding that explains why it was flagged — typically the compared values, the deviation, and the threshold. Evidence makes findings auditable and challengeable.

Also called: evidence, evidenz, preuve, evidence chain

Relations

  • part of Thesis: The evidence chain is declared on the thesis, with a weight per link.
  • is not Finding: A finding is what a signal detected. Evidence is the weighted link from a thesis to a signal. Evidence is the connection, not the finding.

Extractor Engine word

A script declared in pipeline.yml that copies source bytes across the trust boundary without reshaping them. A pack asset, copied into the tenant's afs/scripts/ at init.

Is not
a transformation. An extractor copies; only a declared pre_sync hook may reshape a delivery, and everything else belongs in Bronze
More

Extractors run in Phase 0, are SHA-256 pinned and failure-intolerant, and append to afs/state/extract_log.jsonl. A source system that needs joins or flattening uses a pre_sync hook (e.g. extract_sap_ish.py), the declared exception to the zero-transform rule. See docs/design/extractor_discipline.md and docs/design/pluggable_extractors.md.

Also called: extractor, extract script, pre_sync, pre-sync hook

Relations

  • lives in AFS: Declared in afs/scripts/pipeline.yml, the extraction contract. An extractor copies bytes; only a declared pre_sync hook may reshape.

Finding Engine word

A single anomaly or pattern instance detected by a signal — with a continuous score (0-100), affected entity, and impact assessment.

Is
a specific, attributable detection event
Is not
a "result" or "alert." Use "finding" consistently — never "signal result"
More

A single flagged anomaly produced by a signal. Every finding carries a continuous score (0-100, with display labels derived from ranges), polarity, direction, the affected entity, the time period, structured impact (value + unit + dimension), and machine-readable evidence. Findings are the atomic unit of analytical output.

Also called: finding, signal instance, befund, résultat, constat

Relations

  • is not Evidence: A finding is what a signal detected. Evidence is the weighted link from a thesis to a signal. Evidence is the connection, not the finding.
  • lives in KLS: Every signal_findings table is built into the KLS.
  • produced by Signal: Each signal emits a findings table: one row per detected instance.
  • grouped by Perspective: By computation: findings from several signals become one health score per entity.

Fleet Engine word

All tenants registered in the fleet store (FLS) of one installation. Defined by registration, the way a fleet of ships is what is on the register: the FLS does not describe the fleet, it constitutes it. A fleet is always read through one of three aspects — lfleet, pfleet or ofleet.

Is
the register of what one installation serves
Is not
a view over every tenant an operator can reach — that was Sense 62's definition, replaced 2026-08-31
More

What the FLS registers is presences, not tenants: a tenant on disk is a fact you discover, while "this installation serves tenant X" is a decision somebody made. An unregistered tenant is therefore not missing from the fleet — it is not served. The roster (which tenants exist) stays a projection, computed and never stored. See docs/design/the_fleet_store.md and docs/design/what_is_a_fleet.md.

Also called: fleet store, FLS, register, fleet register

Relations

  • lives in Installation: One fleet store per installation, so two registers are two installations and two fleets.
  • has kind lfleet (logical fleet): The logical aspect: curated sets of tenants.
  • has kind pfleet (physical fleet): The physical aspect: cloud → region → Site.
  • has kind ofleet (organisational fleet): The organisational aspect: a single-parent tree.
  • has part Aspect: Every fleet is read through exactly one aspect, and the aspect is always spoken at a broadcast (Mig, 2026-11-17).

Generation Engine word

A delivery of source data, arriving anywhere from yearly to near-realtime: the timestamp level of source/<channel>/<timestamp>/. A new generation changes no configuration: the same arrangement re-renders on the new data into a new KLS. With the scenario, one of the two keys of a KLS, which is the container (scenario, generation). That keying is the target model; today a new delivery overwrites the working copy.

Is not
a scenario, and not a pipeline stage. The generation is the data axis; the scenario is the state axis. The build/gen00_raw and gen01_canonical directories are stages, an older use of the word
More

branch = state (scenario), render = composition, generation = data. The three are orthogonal. See docs/design/the_daw.md.

Also called: generation, data delivery, delivery, generational, take

Relations

  • lives in source/ (Delivered data): A delivery is a timestamped folder, source/<channel>/<timestamp>/. Not the gen00/gen01 build directories: those are stages.
  • keys KLS: Target, not yet code (ruled 2026-11-20): a new data delivery means a new KLS for every scenario, with no configuration change. Today nothing names the generation and a new delivery overwrites the working copy.

Imprint Engine word

The AFS a given KLS was built from, frozen and zipped inside that KLS (_<tenant>.afs_archive). Its id is the git commit in the KLS's stamp.

Is not
the live AFS. The live AFS moves on; the Imprint is what this KLS actually came from, and a dirty-tree build matches no commit
More

The archive includes .git/, so git log works on an extracted Imprint; whether that stays is open (docs/design/what_the_kls_carries_of_the_afs.md). Today the id is a short commit with no tree hash. Read-only by ruling (2026-08-20). See docs/design/the_imprint.md and jinflow/imprint.py.

Also called: imprint, afs archive, _jinflow_afs_archive, afs_archive

Relations

  • part of KLS: Every KLS carries exactly one: the AFS it was built from, zipped inside it.
  • is not AFS: The AFS is what the next build reads, and it moves. The Imprint is what this KLS was built from, and it never moves.

Installation Engine word

The set of engines that share one fleet store. There is exactly one FLS per installation, so two registers are two installations — and two fleets. An engine that only reads a replica of the FLS (its footing) is a client of the installation, not a member.

Is
the boundary drawn by one fleet store
Is not
a machine
More

Membership is by the book you write to, not the book you read. An installation is a deployment, not a machine: one installation must have one filesystem, or it silently becomes two registers. Rows carry an installation_id so that a table shared by two installations stays separable. See docs/design/the_fleet_store.md §4–§6.

Also called: installations, installation_id

Relations

  • holds Fleet: One fleet store per installation, so two registers are two installations and two fleets.

KLS Engine word

Knowledge Store. A per-tenant DuckDB file containing every Gold table, every signal_findings, every thesis_verdict, every verdict_finding, plus the AFS it was built from as an embedded zip archive (the Imprint). Every KLS is built from one scenario, a state of the AFS held as a git branch; the default branch is a scenario too. A tenant therefore holds many KLSes: the working copy of each scenario ({pack}_{tenant}_kls.duckdb for the default branch, {pack}_{tenant}_{branch}_kls.duckdb for another) and every snapshot. With the DAW a KLS is keyed by (scenario, generation). The KLS is the built picture — read-only, snapshottable, immutable once frozen, and disposable: rebuild it rather than repair it. Sole output of jin make, sole input for jin desk.

More

Knowledge Store. A per-tenant DuckDB file containing every Gold table, every signal_findings, every thesis_verdict, every verdict_finding, plus the AFS it was built from as an embedded zip archive (the Imprint). Every KLS is built from one scenario, a state of the AFS held as a git branch; the default branch is a scenario too. A tenant therefore holds many KLSes: the working copy of each scenario ({pack}_{tenant}_kls.duckdb for the default branch, {pack}_{tenant}_{branch}_kls.duckdb for another) and every snapshot. With the DAW a KLS is keyed by (scenario, generation). The KLS is the built picture — read-only, snapshottable, immutable once frozen, and disposable: rebuild it rather than repair it. Sole output of jin make, sole input for jin desk.

Also called: kls, knowledge store, built picture, ephemeral, ephemeral database, dev.duckdb

Relations

  • part of Tenant: A tenant holds many KLSes: the working copy, every snapshot, and with the DAW one per (scenario, generation). Each KLS belongs to exactly one tenant; there is no cross-tenant data layer.
  • keyed by Scenario: A KLS is a container (scenario, generation), not a coordinate (The DAW).
  • keyed by Generation: Target, not yet code (ruled 2026-11-20): a new data delivery means a new KLS for every scenario, with no configuration change. Today nothing names the generation and a new delivery overwrites the working copy.
  • is not OPS: KLS: derived, disposable, rebuild it. OPS: produced by operation, never rebuilt; restore it from backup (P13).
  • holds Finding: Every signal_findings table is built into the KLS.
  • has kind Snapshot: Frozen and named. make refuses to overwrite it; the working copy is overwritten every time.
  • written by Make: Each make writes exactly one KLS. The working copy is rewritten by every make; a snapshot is written once.
  • has kind Working copy: The KLS a plain make overwrites, <pack>_<tenant>_kls.duckdb, stamped 'working'.
  • has part Imprint: Every KLS carries exactly one: the AFS it was built from, zipped inside it.
  • read by desk (jin desk): Read-only, so it never contends with make for the lock.
  • read by console (jin console): To see what the build found, scoped to one tenant.

Make Engine word

The single build command. Phase 0 extracts source data under the pipeline.yml contract; Phase 0b syncs changed CSVs from the DLZ into source/; the remaining phases enrich, compile, and run dbt deterministically from the complete AFS to produce the KLS.

More

The input phases of make have side effects (extraction, DLZ sync, a git commit); the build phases read the AFS and the tenant's source/ data and write the KLS, plus Run records and the baked identity tree in the OPS. This split across the AFS commit makes every KLS reproducible from a single AFS commit and the same source data, and makes make the security boundary — whoever controls make controls the analytical truth.

Also called: jin make, jinflow make

Relations

  • reads AFS: One AFS commit per build. What it read is packed into the KLS as its Imprint; the commit is only the Imprint's id, and a dirty-tree build matches no commit.
  • reads source/ (Delivered data): The second input of every build, beside the AFS. With the AFS, the only thing a build reads; it never reads the DLZ.
