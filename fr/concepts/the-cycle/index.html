The Cycle — make, explore, evolve, publish

Ce contenu n’est pas encore disponible dans votre langue.

Every jinflow session is a loop through four verbs and three stores. make builds, explore reveals, evolve drafts, publish commits. They all move data through three substrates with strict ownership: the Artefact Store (AFS), the System Information Store (OPS), and the Knowledge Store (KLS).

This page is the map. Every other page in the docs is a zoom-in on one of its arrows.

The picture

Section titled “The picture”

Six steps close the loop. One AI side path joins from the inside.

Read it clockwise: the AFS is the source of truth (declarative YAML). make reads the AFS and builds the KLS (the knowledge store). explore reads the KLS and writes to the OPS (notes, bookmarks, drafts in progress). publish drains the OPS back into the AFS as commits. The loop closes.

evolve is the AI-assisted way to author. It reads the AFS and the KLS, then drafts new YAML directly into the AFS — joining the cycle at the same point as publish. Same destination, different path.

The perimeter — sources, pipeline.yml, Domain Pack Hub, identity — surrounds the cycle but doesn’t change its shape. See The perimeter below.

The four verbs

Section titled “The four verbs”

make — the engine

Section titled “make — the engine”

Reads from DLZ + AFS + OPS. Writes to KLS + AFS. Read-only on OPS.

make is the build pipeline and the security boundary. It runs the extraction contract (Phase 0), syncs the DLZ into the tenant’s source/, validates and enriches CSVs, compiles every YAML in the AFS to SQL, runs dbt to build Bronze → Silver → Gold → signals → theses → verdicts, and stamps the result. The output is a deterministic KLS: identical AFS commit + identical source CSVs = identical KLS bytes. The same KLS also carries the AFS as a zipped BLOB (_jinflow_afs_archive), so it’s literally self-describing — no AFS needed to read what’s inside.

make also runs Phase 1d — Publish SIS → AFS: pending notes and bookmarks that JinDesk dropped into SIS get materialised as AFS commits before the build proceeds. JinDesk owns SIS’s write path; make only reads from it. An mtime fast-skip means SIS isn’t even opened when there’s nothing pending.

See The make guide for the phase-by-phase breakdown.

explore — the UX

Section titled “explore — the UX”

Reads from KLS + OPS. Writes to OPS continuously and to AFS via the Atelier.

explore is the SvelteKit web app users actually open. It reads the KLS read-only (no lock contention with make), reads operational state from OPS (bookmarks, notes, bell), and serves the analytical interface. Three classes of write-back happen here:

  • OPS-resident: notes, bookmarks, scenario state, bell events
  • AFS-resident via the Atelier (Sense 29): signal YAMLs from the Signal Builder, Statements (Subject Matter Level 0), lenses, anything that should survive a rebuild
  • Bell events (Sense 33): pub/sub between writers and readers, persisted in OPS

evolve — the AI colleague

Section titled “evolve — the AI colleague”

Reads from AFS + KLS. Writes to AFS.

evolve is the conversational REPL with read access to one tenant’s KLS and AFS. It can run SQL, inspect the registry, walk lineage from finding to source row, and draft new YAML that it writes directly into the AFS — signals, theses, Subject Matter entries, lenses. Every artefact lands in the AFS the same way a hand-authored one would, and gets built by the next make.

See Tutorial: Exploring with evolve for a session walkthrough.

publish — the OPS-to-AFS umbrella

Section titled “publish — the OPS-to-AFS umbrella”

Reads from OPS. Writes to AFS.

publish (Sense 21 Beat 3) is the explicit boundary that drains the OPS write-back queue into the AFS as a commit. Notes and bookmarks that were OPS-resident during exploration get materialised as YAML in the AFS, and the publish event itself is logged to publish_log.jsonl (Sense 47). Without publish, OPS state stays local; with it, the work becomes part of the durable record.

The three stores

Section titled “The three stores”

Artefact Store (AFS)

Section titled “Artefact Store (AFS)”

A git repo per tenant containing every declarative artefact: signals, theses, verdicts, Subject Matter, Dossiers, lenses, perspectives, entities, contracts, glossary, pipeline.yml, brand config, dbt models. This is the source of truth for what should be computed. Every commit is attributed by The Scribe; the AFS history is the audit trail for the analysis.

Writers: init, evolve, make (during the publish-OPS-to-AFS phase), explore via the Atelier, publish. Readers: make, explore, evolve.

System Information Store (OPS)

Section titled “System Information Store (OPS)”

A DuckDB file per tenant containing operational state: bookmarks, notes-in-progress, bell events, scenario state, transient drafts. OPS is the working surface — fast, mutable, local. Anything in OPS that wants to survive a rebuild migrates to AFS via publish (or via make’s Phase 1d if the next build runs first).

JinDesk owns OPS. It’s the only writer; it owns the schema lifecycle. Everyone else — make, publish, evolve — is read-only on OPS. This is a load-bearing invariant (it eliminated a class of DuckDB version-mismatch corruption when it landed in April 2026).

Writers: explore (continuous, exclusive). Readers: make (Phase 1d), publish, explore.

Knowledge Store (KLS)

Section titled “Knowledge Store (KLS)”

A DuckDB file per tenant containing every Gold table, every signal_findings table, every thesis_verdict, every verdict_finding, plus the embedded AFS archive. The KLS is the built picture — read-only, snapshottable, immutable once frozen. It’s what JinDesk reads and what evolve queries.

Writers: make only. Readers: explore, evolve.

The perimeter

Section titled “The perimeter”

DLZ (Sense 31) — the trust boundary for source data. Every CSV crossing it is declared in pipeline.yml, pinned by SHA-256, verified on every run, and logged in extract_log.jsonl. Bytes that don’t match the pin don’t enter.

Domain Pack Hub — the registry of analytical frameworks (nuMetrix, hrcentral, Millésime, etc.). jin init --pack <name> copies a pack’s starter kit into a new tenant AFS; jin afs update upgrades a tenant’s AFS to a newer pack version. After init, the pack is out of reach — the tenant AFS runs independently.

jinflow.central — the identity plane. Clerk-backed sign-in, role assignment, dev/prod environment routing, deploy machinery. Per-tenant work doesn’t touch it; per-organisation work does.

What changed since the old picture

Section titled “What changed since the old picture”

If you’ve seen the hand-drawn sketch from early 2026, the cycle’s shape hasn’t changed — but the write-back loop has grown a small system around it (Atelier → Bell → publish → Scribe), and the source intake has gone from one “from client” arrow to a contracted boundary (pipeline.yml + extract_log.jsonl). The vocabulary also matured: Probes → Signals, Hypotheses → Theses, SMEbits → Subject Matter, Use Cases → Dossiers. The substrates and the verbs survived the rename.
